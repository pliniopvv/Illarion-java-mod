Visão Geral do Projeto

O Illarion é um jogo de RPG multiplayer online (MMORPG) desenvolvido e mantido pela Illarion e.V., uma organização sem fins lucrativos. Este repositório contém todas as aplicações publicadas do projeto, incluindo o cliente do jogo, editores de NPC e missões, editor de mapas e utilitários de download/atualização.

Nota: O projeto é desenvolvido voluntariamente por membros da comunidade Illarion. Contribuições são bem-vindas através de pull requests.

Objetivos do Projeto

  • Fornecer um cliente de jogo completo e funcional para os jogadores
  • Oferecer ferramentas de edição para criadores de conteúdo (NPCs, missões, mapas)
  • Manter um sistema de atualização simples e eficiente
  • Promover a modularidade e reutilização de código

Repositórios Relacionados

  • Servidor: Código do servidor do jogo (não incluído neste repositório)
  • Recursos: Pacotes de recursos (gráficos, sons, tabelas) distribuídos separadamente
  • Site: https://illarion.org

Arquitetura do Sistema

Visão Geral da Arquitetura

A arquitetura do projeto Illarion segue um design em camadas, com clara separação entre a lógica de jogo, renderização gráfica e interface com o usuário. O motor de jogo abstrai as dependências de plataforma, permitindo múltiplas implementações.

Padrões de Design Utilizados

  • Singleton: Utilizado em classes como IllaClient, World, ConfigSystem
  • Factory: EngineManager para criação de instâncias do motor
  • Observer: Sistema de eventos usando EventBus para comunicação entre componentes
  • Strategy: Diferentes backends (libGDX, Nifty) implementam a mesma interface
  • State Machine: Máquina de estados do jogo (Game.STATE_*)
  • Command: Comandos de rede (illarion.client.net.client.*Cmd)

Fluxo de Dados

  1. Entrada: O jogador interage via teclado/mouse → Input captura
  2. Processamento: Lógica do jogo processa a entrada → Game atualiza estado
  3. Rede: Comandos enviados/recebidos → Net gerencia conexão
  4. Renderização: Estado atual é desenhado → Graphics renderiza
  5. Interface: Elementos de UI atualizados → Nifty-GUI exibe

Motor de Jogo (Game Engine)

Componentes Principais

Engine (Interface)

A interface org.illarion.engine.Engine define o contrato para acesso aos componentes principais do motor:

  • getGraphics() - Acesso ao sistema de renderização
  • getInput() - Acesso ao sistema de entrada (teclado/mouse)
  • getSounds() - Acesso ao sistema de áudio
  • getAssets() - Acesso ao gerenciador de recursos

Backend libGDX

Implementação principal de renderização usando libGDX com LWJGL3. Responsável por:

  • Renderização 2D de sprites e tiles
  • Gerenciamento de texturas e atlas
  • Efeitos gráficos (iluminação, névoa, highlight)
  • Gerenciamento de janela e resolução
  • Suporte a fullscreen e VSync

Backend Nifty-GUI

Implementação de interface gráfica usando Nifty-GUI. Responsável por:

  • Renderização de elementos de UI (janelas, botões, campos)
  • Gerenciamento de layouts e temas
  • Integração com o sistema de input
  • Suporte a controles personalizados

Gerenciamento de Recursos

O motor de jogo utiliza um sistema de carregamento assíncrono de recursos:

  • TextureManager: Carregamento e cache de texturas
  • SoundsManager: Carregamento de efeitos sonoros e música
  • FontManager: Gerenciamento de fontes tipográficas
  • EffectManager: Gerenciamento de efeitos gráficos
  • CursorManager: Gerenciamento de cursores personalizados

Sistema de Estados do Jogo

O cliente do jogo utiliza uma máquina de estados para controlar o fluxo:

  • STATE_LOGIN - Tela de login e autenticação
  • STATE_LOADING - Carregamento de recursos
  • STATE_GAME - Jogo principal (mundo, combate, etc.)
  • STATE_LOGOUT - Processo de logout
  • STATE_ENDING - Encerramento do cliente

Comunicação com o Servidor

Visão Geral do Sistema de Rede

O sistema de comunicação do cliente Illarion é responsável por toda a troca de dados entre o cliente e o servidor do jogo. Ele utiliza uma arquitetura baseada em threads com NIO (New I/O) para garantir comunicação eficiente e de baixa latência.

Protocolo: TCP com NIO (SocketChannel) | Encoding: ISO-8859-1 | KeepAlive: 500ms | Buffer: Dinâmico (mínimo 1000 bytes)

Componentes Principais

NetComm - Gerenciador Central

A classe illarion.client.net.NetComm é o ponto central de toda a comunicação. Ela gerencia o ciclo de vida da conexão, coordena as threads de envio e recepção, e implementa o sistema de KeepAlive automático.

  • Conexão: Estabelece e gerencia o SocketChannel com o servidor
  • Threads: Cria e coordena Sender, Receiver e MessageExecutor
  • KeepAlive: Envia pacotes KeepAlive a cada 500ms para manter a conexão ativa
  • Desconexão: Gerencia o desligamento gracioso de todas as threads

Receiver - Thread de Recepção

A classe illarion.client.net.Receiver é uma thread dedicada que recebe dados do servidor, decodifica as mensagens e as prepara para execução.

  • Decodificação: Lê bytes do socket e converte em mensagens estruturadas
  • Validação: Verifica CRC e estrutura do header para garantir integridade
  • Buffer: Usa ByteBuffer dinâmico para otimizar memória
  • Timeout: Descarta dados incompletos após 1 segundo sem recebimento

Sender - Thread de Envio

A classe illarion.client.net.Sender é responsável por codificar comandos do cliente e enviá-los ao servidor de forma assíncrona.

  • Codificação: Converte comandos Java em bytes para transmissão
  • CRC: Calcula checksum para verificação de integridade no servidor
  • Fila: Usa ExecutorService para envio assíncrono
  • Buffer: ByteBuffer direto de 1000 bytes para otimização

MessageExecutor - Processador de Mensagens

A classe illarion.client.net.MessageExecutor gerencia a execução das mensagens recebidas do servidor em uma thread separada.

  • Fila de Execução: Executa mensagens sequencialmente em uma única thread
  • Reschedule: Permite reagendar mensagens que não puderam ser processadas
  • Tratamento de Erros: Captura e loga exceções durante a execução

ReplyFactory - Fábrica de Respostas

A classe illarion.client.net.ReplyFactory é um factory singleton que mapeia IDs de mensagens para suas respectivas classes decodificadoras.

  • Registro: Registra 52 tipos diferentes de mensagens do servidor
  • Instanciação: Cria instâncias sob demanda usando reflexão
  • Anotações: Usa @ReplyMessage para mapear IDs automaticamente

Formato do Protocolo

Estrutura do Pacote

Toda comunicação segue um formato de pacote específico com header fixo de 6 bytes:

Campo Tamanho Descrição
ID 1 byte Identificador do comando/mensagem
XOR ID 1 byte ID XOR 0xFF para validação do header
Length 2 bytes Tamanho dos dados em bytes (unsigned short)
CRC 2 bytes Checksum para verificação de integridade
Data Length bytes Dados específicos do comando/mensagem

Validação de Integridade

  • XOR Check: O segundo byte deve ser igual ao primeiro XOR 0xFF
  • CRC Check: Checksum calculado sobre os dados deve corresponder ao CRC do header
  • Timeout: Dados incompletos são descartados após 1 segundo

Fluxo de Comunicação

Envio de Comando (Cliente → Servidor)

  1. Criação: O cliente cria uma instância do comando (ex: MoveCmd)
  2. Envio: NetComm.sendCommand(cmd) é chamado
  3. Fila: O comando é adicionado à fila do Sender
  4. Codificação: Sender.encodeCommand() converte o comando em bytes
  5. CRC: Checksum é calculado e adicionado ao header
  6. Transmissão: Bytes são enviados via SocketChannel

Recebimento de Mensagem (Servidor → Cliente)

  1. Leitura: Receiver lê bytes do socket para o buffer
  2. Validação: Header é verificado (XOR ID, Length, CRC)
  3. Decodificação: ReplyFactory.getReply(id) cria a instância apropriada
  4. Parsing: ServerReply.decode(reader) extrai os dados
  5. Fila: Mensagem é adicionada ao MessageExecutor
  6. Execução: ServerReply.execute() processa a mensagem

Tratamento de Erros

  • Conexão Perdida: IllaClient.sendDisconnectEvent() é chamado com opção de reconexão
  • CRC Inválido: Pacote é descartado e logado como warning
  • ID Desconhecido: Mensagem é ignorada e logada como erro
  • Timeout: Dados incompletos são descartados após 1 segundo
  • Exceção: Erros são logados e a mensagem pode ser reagendada
